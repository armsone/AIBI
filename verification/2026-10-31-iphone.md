## Root causes — demonstrated vs hypothesis

### ChatGPT collapsed sidebar (Stargram iOS login probe and login sheet)

- Demonstrated in source: `ExternalAILoginProbeBridge.checkAuthStatus` clicked the open-sidebar control at
  most once per navigation (`sidebarOpenAttempted`), and page readiness is `document.readyState`
  interactive (pre-hydration). A click that WebKit delivers before the SPA attaches its handler returns
  `clicked: true`, consumes the only attempt, and nothing re-opens the sidebar; the account markers stay
  hidden until a human taps it, which is exactly the device behavior. Android already retries bounded
  (every other poll, ≤8 attempts) and its 2026-08-29 device trace needed three polls before the marker hydrated.
- Not proven: that the current mobile control still matches the documented selector
  (`button[aria-label='사이드바 보기'][aria-controls='browser-sidebar-popover'][aria-expanded='false']`,
  2026-10-17 trace). If it no longer matches, the retry change cannot help; see device checks.
- Fix: bounded retry (`maxSidebarOpenAttempts = 6` per navigation). A click is attempted only when the
  provider-specific probe is ambiguous (no auth, login or challenge marker), only on exactly one visible
  closed control (unchanged script), and authentication still comes only from provider-specific account
  markers. No generic composer/cookie/URL evidence was added.

### Claude collapsed sidebar

- Demonstrated in source: the reveal step is gated `provider == .openAI`; Claude has no reveal path on
  iOS (nor on Android), and its account markers (`user-menu-button` etc.) are only exposed after opening
  the sidebar per the device observation.
- Final candidate (selector HYPOTHESIS, current DOM attributes NOT observed): the gate is now
  `ExternalAIBrowserScripts.openSidebarScript(for:)` (ChatGPT script unchanged, Claude new, Gemini/Grok nil).
  `openClaudeSidebarScript` clicks only when exactly one visible `button` has the exact `aria-label`
  `Open sidebar` or `사이드바 열기`; aria-hidden/inert/hidden clones are ignored, more than one visible match,
  `aria-expanded='true'`, disabled/aria-disabled → no click. No generic menu/toggle, no editor-based auth.
  Same ambiguity precondition (no auth/login/challenge marker), same per-navigation bound (6), and
  authentication still only from Claude account markers (`user-menu-button` etc.) re-probed after the click.
  If the labels do not match on device, nothing is clicked and the probe stays unknown (prior behavior).
  Synthetic fixture `fixtures/providers/claude-ios-collapsed-sidebar-hypothesis.json` (`observedOnDevice: false`).
- If it fails on device, TM trace needed: for the closed control only, tag, exact `aria-label`,
  `aria-expanded`, `aria-controls`, `data-testid` presence/value, visible vs hidden clone count.
- Deferred by instruction: Android and other canonical host adapters are NOT changed until the iPhone
  candidate is proven.

### Gemini text-only failure

- Demonstrated from trace + source: (1) readiness came from the readyState poll after commit, so the first
  `.task(id: navigationGeneration)` filled at 787 ms, before didFinish; (2) didFinish increments
  `navigationGeneration`, cancelling that task inside `submitPromptWhenReady` (cancellation exits without
  send_timeout, matching the trace); (3) the replacement task ran its full 45 s deadline without one
  successful fill (every successful fill logs prompt_inserted; 3043 + 45000 + one 700 ms sleep ≈ 48753).
  (4) `prompt_length` is `textContent`, which omits the `<br>` line breaks the fill inserts, so 479 vs 444
  is a measurement artifact candidate, not proof of lost text.
- Demonstrated source defect (lifetime): every didFail/didFailProvisional — including the cancellation of a
  navigation superseded by a newer one — called `markNavigationFinished()`, which logged `browser_loaded`,
  set `isPageReady = true` and restarted the fill task while the newer document might not be committed or
  injected yet. Fixed with a latest-navigation identity check; superseded callbacks now only log
  `browser_load_failed` (failure_kind 1 cancelled / 3 other) and never mark the page ready.
- Final candidate fix for (1)–(2), the demonstrated same-document lifetime defect: `navigationGeneration`
  had exactly one increment site, `markNavigationFinished` (called from didFinish, non-superseded
  didFail/didFailProvisional, renderer termination). It now increments only when the document actually
  changes: `didCommitNavigation` (non-superseded commit) and `markRendererTerminated` (WebContent process
  death). didFinish/failure of the same document only marks ready (and cancels the readyState poll), so a
  task that filled after `bridge_ready` keeps running through submit. Epoch/stale-callback handling
  (`docEpoch`, `latestNavigation`/`isSuperseded`) and `.task(id:)` cancellation are unchanged.
  Post-send safety in both loops (hidden automator and sheet): a cancelled task no longer reports
  "전송 뒤 응답 시작을 확인하지 못했어요" (it returns silently), and a task restarted by a real new
  document after `hasAttemptedSubmission` only verifies (no fill — `fillPrompt` also guards — and
  `submitPrompt` skips the click when an attempt is recorded). A provisional failure of the very first
  load no longer restarts the task with a fresh deadline; the running task continues on its own deadline.
- Hypotheses NOT proven by the existing trace (no snapshot after 2098 ms despite later blank page; old
  builds did not log navigation start/commit or fill rejection): (a) a later main-frame navigation replaced
  the document with one that never became interactive/observer-injected, or (b) `__starManagerSendPrompt`
  rejected the click because normalized composer text differed from the inserted prompt, followed by a
  fill rejection. No selector or send gate was changed for Gemini.
- Added sanitized discriminators (existing allowlisted keys plus two new stage names):
  `navigation_started`, `navigation_committed`, `bridge_ready` (readyState readiness), `browser_load_failed`
  with failure_kind, `prompt_failed` (observer rejected fill) / `bridge_failed` (helper missing or eval error),
  each fill failure kind logged once per streak, and `bridge_snapshot.prompt_present` = normalized
  composer text equals last inserted prompt (0/1, no text). Adapter label is now `aibi-stargram-0.5.5`.

### Source reasoning

1. Send wait could never pass (demonstrated): `__starManagerSendPrompt` sends only if the normalized composer
   text equals `__starManagerLastFilled`. From 1964 ms the hydrated composer held different text, so the
   sheet's 15 s `submitPromptWhenReady` loop polled an impossible condition: 1182 + 15000 ≈ 16205 send_timeout.
2. bridge_failed at 16974 (= 16205 + 700 ms sleep + one eval) is the sheet's refill `fillPrompt(force: true)`,
   not a reload: the document never changed (no navigation event after 342), and nothing in the adapter
   deletes the per-document helpers. `bridge_failed` (not `prompt_failed`) means the evaluation threw or
   returned a non-boolean; the helper itself only returns booleans. In its contenteditable path the only
   statement that can throw is `document.execCommand('insertHTML', false, string)` — an HTML string sink
   (INFERENCE, not physically confirmed: a Trusted Types-enforcing document would throw TypeError for plain strings). Pre-fix iOS had no try/catch there,
   unlike the canonical runtime (`aibi-browser-runtime.js`) and Android `ExternalAIScripts.kt`, so each
   700 ms refill until the 45 s deadline failed the same way (logged once per streak; no further snapshot).
   Eval exception vs helper-missing was NOT recorded by that build (bridge_failed had no metric) → see (5).
3. Quill line-break hypothesis (INFERENCE from source + general editor behaviour, not physically confirmed;
   the trace proves only the normalized mismatch): Gemini's composer is Quill (`div.ql-editor`). The old
   route inserted `<br>`-separated HTML; Quill removes a `<br>` that has siblings in a block, so line breaks
   cannot survive in a hydrated ql-editor even when insertHTML does not throw. Consistent with 479 → 444
   (textContent) and prompt_present 0; the exact hydration transform remains unrecorded (no text logged).
4. Why the first fill passed pre-hydration and only later ones failed: not proven (the 1262 snapshot's
   textContent 479 implies the first write was not the `<br>` HTML; most likely the text-node fallback after
   insertHTML returned false). It does not change the fix.

### Fix (ExternalAIBrowserView.swift, synced to Stargram)

- `__starManagerFillPrompt`, Quill editor (`el.classList.contains('ql-editor')`) only: select all, native
  editing `execCommand('insertText')` (typing route, line breaks become paragraph separators; try/catch);
  if it fails or the normalized full contents differ, replace with Quill's own paragraph structure built via
  DOM APIs (`<p>line</p>`, empty line `<p><br></p>`; no HTML string sink) and dispatch `input`; if the
  normalized full contents still differ, return false (no `__starManagerLastFilled` update). Same
  `__starManagerSubmitDispatched` and force guards as before. Non-Quill editors keep insertHTML, now wrapped
  in try/catch with the existing text-node fallback (runtime/Android parity). ChatGPT/Claude paths otherwise
  unchanged.
- Bounded pre-send recovery: new `__starManagerPromptState()` (numeric only: 3 dispatched, 0 not
  ready/no editor/not filled/readyState≠complete, 1 match, 2 loaded composer differs).
  `bridge.isPromptReplacedBeforeSend()` returns true only if `hasAttemptedSubmission` is false, the state is 2,
  and successful fills so far are 1…2 (`maxPromptFillsBeforeSend = 3`); it logs
  `send_blocked {prompt_present: 0, attempt: n}`. Both `submitPromptWhenReady` loops (sheet and hidden
  automator) check it only after a `submitPrompt()` that did not send, and then return false immediately
  (no 15 s wait, no send_timeout); the existing outer loops refill with `force: true` and re-enter the
  unchanged send gate. After the bound the previous 15 s behaviour applies; the 45 s deadline still ends it.
- Not relaxed: normalized full-text match in `__starManagerSendPrompt`, attachment count gate in
  `submitPrompt`, `__starManagerSubmitDispatched`/`hasAttemptedSubmission` exactly-once, fill refused after a
  click (JS) or recorded attempt (Swift); an ambiguous/confirmed submission is never refilled or replayed.
- Diagnostics (AIBIDiagnosticsStore.swift, existing keys only): `prompt_inserted.attempt` (successful fill
  number), `send_blocked.prompt_present 0`, `bridge_failed.failure_kind` 2 page TypeError / 3 other eval
  error / 4 helper missing or unsupported result (range 1…3 → 1…4; only the WKError domain/code and the
  exception-name prefix are inspected, never stored). No text, URL, DOM or account data.
